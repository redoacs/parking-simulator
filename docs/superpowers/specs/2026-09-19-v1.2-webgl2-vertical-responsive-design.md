# v1.2 — WebGL2, vertical scenes, responsive layout

Date: 2026-09-19. Extends `2026-09-18-parking-simulator-design.md` (the v1 spec);
where the two disagree, this one wins and §"Changes to the v1 spec" lists the edits.

## Purpose

Make the simulator usable on mainstream phones, and make the drive keys match
what the car does on screen.

Target devices, chosen by the user: iPhone 17 Pro (Safari and Chrome), a recent
Samsung Galaxy S, a mid-tier Android (Galaxy A56 taken as the hard case), all on
current Chrome or Safari; plus today's desktop browsers.

## Decisions

| Decision | Choice | Why |
|---|---|---|
| GPU API | WebGL2 replaces WebGPU. No dual backend. | WebGPU was not a goal in itself. Per the gpuweb implementation-status wiki (read 2026-09-19), Chrome on Android does not yet ship WebGPU for Samsung Xclipse GPUs — the Exynos Galaxy S26/S26+ and the A56 — and Firefox ships it on neither Linux nor Android. A fallback would mean writing every render feature twice. Nothing the app draws needs WebGPU. |
| Orientation | Each scene is laid out so the car starts pointing up the screen. The view does not rotate afterwards. | Up/down keys match forward/reverse at the start and through a parallel park; the scene stays still, so position against the spot is easy to judge; a street running up the screen suits phone portrait. A heading-up camera was considered and rejected: the spot and swept path would spin as the car steers, and it needs rotation through camera, pan, zoom, fit and every shader. |
| Phone layout | Split thumbs: scene fills the screen, steering under the left thumb, forward/reverse under the right, settings in a sheet. | Reversing while steering needs two held buttons at once; one cluster makes that a stretch for one thumb. |
| Delivery | Three PRs, in the order below. | The port goes first so the other two are written once. Each PR is independently reviewed. |

## PR 1 — WebGL2 replaces WebGPU

A like-for-like port. No visible change is intended.

**Seam.** `Renderer` keeps its public surface — `create`, `camera`, `resize`,
`frame(FrameInput)`, `resetEnvelope`, `rebuildEnvelope`, `readEnvelopeAt` — so
`App` and `src/app.test.ts` are untouched. One leak is closed: `main.ts` reads
`renderer.device.lost` today; it becomes `renderer.onContextLost(cb)`.

**Context.** `canvas.getContext('webgl2', { alpha: false, antialias: false, depth: false, stencil: false })`.
No context → `WebGlUnavailableError`, shown in `#fatal` with wording that names
WebGL2. `src/render/gpu.ts` is replaced by `src/render/gl.ts`.

**Shaders.** The four WGSL files become GLSL ES 3.00 vertex/fragment pairs with
the same maths: `vertex_index` → `gl_VertexID`, `fwidth` is core, the camera
uniform stays one 32-byte std140 uniform block bound at index 0 for every
program, ring instances use `vertexAttribDivisor` + `drawArraysInstanced`.

**Envelope.** Same design: an `R8` texture attached to a framebuffer,
`blendEquation(MAX)` while accumulating footprints, sampled with linear
filtering when composited. `readEnvelopeAt` uses `readPixels` with
`RGBA`/`UNSIGNED_BYTE` (the combination every implementation must accept) and
returns the red channel. It stays `Promise`-returning so callers do not change.
Texture size is clamped to `MAX_TEXTURE_SIZE` as it is to
`maxTextureDimension2D` today.

**Draw order** is unchanged: grid, static polygons, envelope, rings, dynamic
polygons, over the same clear colour.

**Context loss.** `webglcontextlost` replaces `device.lost`. Policy is
unchanged: `decideOnDeviceLoss` reloads unless the previous loss was under
60 s ago, and then shows the message. Restoring in place is out of scope.

**Removed.** `@webgpu/types`, the WGSL files, `gpu.ts` and its
`eslint-disable`, the WebGPU wording in `main.ts` and the README.

**Tests.** Unit tests are unchanged (nothing GPU-side is unit-tested today).
The e2e suite is the acceptance test, including the envelope read-back; its
"no WebGPU" case becomes "no WebGL2" by stubbing `getContext`. The five
SwiftShader flags in `playwright.config.ts` and the Vulkan packages in CI are
removed only if e2e is observed passing without them; otherwise they stay and
the PR says so. Before/after screenshots of the three presets are attached to
the PR for a by-eye check — the two APIs do not rasterise identically, so no
pixel-equality claim is made.

## PR 2 — scenes start with the car pointing up

No camera or shader change.

A helper `rotateScene(scene, quarterTurns)` in `src/scene/` rotates obstacles,
target, bounds and the start pose by a multiple of 90°. A rigid rotation keeps
polygon winding and keeps left and right where they were. Presets are still
described in their natural frame and rotated as the last step of `build`:

- **parallel**: +90°. The street runs up the screen; kerb and spot on the car's right.
- **perpendicular**: −90°. The car starts heading up the aisle; the bay is on its right.
- **garage**: approach 0 already points up; approach 90 is rotated −90°, putting the garage on the car's right.

Params and the URL hash are unchanged. Targets stay axis-aligned rectangles, so
`parkedOffsets` needs no change.

**Tests.** Every preset, at every approach, starts with `theta = π/2`.
`rotateScene` is unit-tested: four quarter-turns are the identity, winding and
area are preserved, bounds still contain everything. The existing validity grid
covers the rotated scenes as-is. The e2e drive assertions move from x to y.

## PR 3 — responsive layout and touch

**Layouts.** Wide (≥ 900 px and a fine pointer): unchanged — sidebar and scene.
Otherwise the compact layout:

```
┌───────────────────────┐
│ clearance 23.4 cm   ☰ │   HUD and menu button
│        scene          │   fills the screen
│ ⟲  C            −  +  │   rewind, centre steering · zoom
│ ◀ ▶               ▲   │   left thumb steers
│                   ▼   │   right thumb drives
└───────────────────────┘
```

☰ opens the existing panel as a sheet over the scene (scenario, parameters,
readouts, time scale, reset, fit, vehicle data). It is the same DOM, moved by
CSS, not a second panel. The overlay buttons use the existing
`DriveInput.bind`, which is already per-pointer, so two thumbs can hold two
buttons at once. The panel's own drive pad is hidden in the compact layout.

**Gestures.** One finger pans, as today. Two fingers pinch-zoom about their
midpoint and pan with it. The gesture maths is a pure function on `Camera`
(previous and current pointer pairs in, pan and zoom out) and is unit-tested.
A finger that goes down on an overlay button never pans.

**Phone details.** `viewport-fit=cover` with `env(safe-area-inset-*)` padding;
`100dvh` so browser bars do not cover the pad; `user-select: none`,
`-webkit-touch-callout: none` and a suppressed context menu on the controls;
touch targets ≥ 48 px.

**Bounds.** 320 px wide up to desktop, portrait and landscape. Below 320 px is
not supported.

**Tests.** Playwright with phone emulation and touch: the overlay is shown and
the sidebar is not; two simultaneous touches move and steer the car; ☰ opens
and closes the sheet; at desktop size the overlay is absent. The real check is
on the user's iPhone, over the LAN with `pnpm dev --host` before merge (WebGL2
does not need a secure context; this is expected to work and is verified then).

## Out of scope

Obstacle editor; heading-up camera or a toggle for it; restoring a lost GL
context in place; making the e2e job merge-blocking; the remaining v1 deferred
minors; any WebGPU path.

## Changes to the v1 spec

Applied in the PR that makes each one true: the Decisions row "GPU stack" and
§5's "seam for a later WebGL2 or 3D backend" (PR 1); §2's preset frames (PR 2);
§6's layout and button list (PR 3); §10 drops "WebGL2 fallback" (PR 1).
